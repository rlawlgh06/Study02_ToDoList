- **문서 상태**: 설계 확정 (구현 전)
- **작성일**: 2026-10-02
- **대상 저장소**: Study02_ToDoList

## 1. 개요

### 1.1 목적

바닐라 자바스크립트로 개인용 할 일 관리 앱을 만든다. **주된 목적은 학습**이며, 프레임워크 없이 상태 관리·DOM 렌더링·데이터 영속화의 기본기를 익히는 것이 목표다.

결과물은 브라우저에서 단독으로 동작하는 단일 화면 웹앱이다.

### 1.2 사용자

문서 작성자 본인 1명. 다중 사용자, 계정, 인증은 고려하지 않는다.

### 1.3 사용 규모

하루 10~20개의 할 일을 관리한다. 이 규모 가정이 아래 여러 설계 결정의 근거가 된다.

### 1.4 외부 요건

없음. 정해진 과제 채점 기준이나 제출 양식이 없으므로, 성공 기준은 2장에서 자체 정의한다.

## 2. 성공 기준

### 2.1 기능 기준

- 9장의 수동 검증 체크리스트 전 항목 통과
- 정상 사용 중 브라우저 콘솔 에러 0건
- 9.1의 자동 테스트 전 항목 통과

### 2.2 학습 기준

구현을 마친 뒤 다음 다섯 가지를 스스로 설명할 수 있어야 한다. 이 문서의 가장 중요한 성공 지표다.

1. 왜 DOM이 아니라 상태가 진실의 원천(source of truth)인가
2. 전체 재렌더가 왜 이 규모에서 괜찮은가, 그리고 언제부터 괜찮지 않게 되는가
3. 이벤트 위임이 전체 재렌더 방식과 어떤 관계인가
4. 무엇을 저장하고 무엇을 저장하지 않는가 — 영속 데이터와 UI 상태의 구분
5. 파생값(진행률)을 저장하지 않는 이유

## 3. 범위

### 3.1 포함

- 할 일 추가, 수정, 삭제
- 완료 체크 / 해제
- 카테고리 분류 (업무 / 개인 / 공부)
- 카테고리별 필터링
- 진행률 표시
- 완료 항목 일괄 정리
- 새로고침 후 데이터 유지

### 3.2 의도적 제외

아래 기능은 **없어서 빠진 것이 아니라, 범위를 지키기 위해 의도적으로 제외**한다. 추후 추가를 검토할 때 이 기록을 판단 기준으로 삼는다.

| 제외 항목 | 제외 사유 |
|---|---|
| 마감일 / 날짜 | 날짜 비교 로직과 "오늘" 경계 처리가 학습 초점을 흐린다 |
| 우선순위 | 카테고리로 이미 분류 축이 하나 있다. 축을 둘로 늘리면 필터 조합 문제가 생긴다 |
| 드래그 정렬 | HTML5 Drag & Drop API는 그 자체로 별도 학습 주제 |
| 검색 | 10~20개 규모에서는 눈으로 찾는 편이 빠르다 |
| 태그 | 카테고리와 역할이 중복된다 |
| 반복 할 일 | 날짜 개념이 전제되어야 한다 |
| 서브태스크 | 트리 구조는 상태 관리 난이도를 크게 올린다 |
| 알림 | Notification API 권한 처리는 별도 주제 |
| 다크 모드 | 기능이 아닌 스타일. 핵심 학습 목표와 무관 |
| 다중 기기 동기화 | 서버가 필요하다. 이 앱은 클라이언트 단독 |
| 실행취소(undo) | 되돌리기 스택은 별도 학습 주제 |

## 4. 기능 요구사항

### FR-1. 할 일 추가

- 입력창에 텍스트를 입력하고 **Enter** 또는 **추가 버튼**으로 등록한다.
- 등록 시 카테고리를 함께 선택한다. 기본값은 `업무`.
- `trim()` 후 빈 문자열이면 **등록을 거부**한다. 조용히 무시하지 말고 시각적 피드백(입력창 테두리 강조 등)을 준다.
- 텍스트는 **최대 200자**로 제한한다.
- 등록 후 입력창은 비우되 **포커스는 유지**한다. 연속 입력을 위한 요구사항이다.

### FR-2. 할 일 수정

- 각 항목의 수정(✎) 버튼을 누르면 해당 줄의 텍스트가 입력 필드로 전환된다.
- **Enter**: 저장 / **Esc**: 취소하고 원래 텍스트로 복원 / **포커스 이탈(blur)**: 저장
- 수정 시에도 FR-1의 빈 문자열·200자 규칙을 동일하게 적용한다.
- 동시에 편집 가능한 항목은 **1개**로 제한한다 (`editingId` 단일 값).

### FR-3. 할 일 삭제

- 삭제(🗑) 버튼을 누르면 `confirm()`으로 한 번 확인 후 삭제한다.
- 실행취소는 제공하지 않는다 (3.2 참조).

### FR-4. 완료 체크

- 체크박스로 완료 / 미완료를 전환한다.
- 완료된 항목은 시각적으로 구분한다 (텍스트 취소선, 흐린 색).
- 완료 항목도 목록에서 **사라지지 않는다**.

### FR-5. 카테고리 분류

- 카테고리는 `업무`, `개인`, `공부` **세 가지 고정값**이다. 사용자가 추가·수정·삭제할 수 없다.
- 각 항목에 카테고리 배지를 표시한다.

### FR-6. 카테고리 필터

- 필터 버튼: `전체`, `업무`, `개인`, `공부`
- 선택된 필터는 시각적으로 구분한다.
- 필터는 **목록 표시만** 거른다. 진행률에는 영향을 주지 않는다 (FR-7 참조).
- 필터 상태는 저장하지 않는다. 새로고침하면 `전체`로 돌아간다.

### FR-7. 진행률 표시

- `완료 개수 / 전체 개수`와 백분율을 함께 표시한다. 예: `4 / 15 완료 (27%)`
- 진행률 막대(progress bar)를 함께 렌더링한다.
- **전체 할 일 기준으로 계산한다.** 선택된 카테고리 필터와 무관하다.
  - *근거*: "업무 탭에서 보는 진행률"이 전체 진행인지 업무만의 진행인지 모호해진다. 항상 전체 기준으로 고정해 해석의 여지를 없앤다.
- 할 일이 **0개일 때 0%**로 표시한다. 0으로 나누지 않도록 주의한다.

### FR-8. 완료 항목 일괄 정리

- "완료 항목 비우기" 버튼으로 `done: true`인 항목을 모두 삭제한다.
- `confirm()`으로 한 번 확인한다.
- 완료 항목이 0개면 버튼을 비활성화한다.

> **설계 근거**: 완료 항목이 무한히 쌓이면 하루 15개 기준 한 달 뒤 약 450개가 되어 진행률이 영원히 100%에 닿지 못하고 목록도 사용 불가능해진다. 날짜 기반 자동 리셋 대신 수동 정리를 택한 이유는 ① 사용자 데이터를 자동 삭제하지 않아 안전하고 ② 날짜 로직이 없어 학습 초점이 CRUD·상태·렌더링에 유지되기 때문이다.

### FR-9. 데이터 영속화

- 모든 할 일은 `localStorage`에 저장한다.
- 추가 / 수정 / 삭제 / 완료 전환 / 일괄 정리 **직후 즉시 저장**한다.
- 새로고침, 브라우저 재시작 후에도 데이터가 유지된다.

### FR-10. 빈 상태 안내

다음 두 경우에 **서로 다른 안내 문구**를 표시한다.

| 상황 | 문구 예시 |
|---|---|
| 할 일이 하나도 없음 | "첫 할 일을 추가해 보세요" |
| 필터 결과만 없음 | "'공부' 카테고리에 할 일이 없습니다" |

## 5. 데이터 모델

### 5.1 Todo 객체

```js
{
  id: "1735800000000",              // 생성 시각 기반 문자열
  text: "PRD 리뷰하기",              // 1~200자
  category: "업무",                  // "업무" | "개인" | "공부"
  done: false,
  createdAt: "2026-10-02T09:00:00.000Z"
}
```

### 5.2 애플리케이션 상태

```js
{
  todos: [],          // Todo[]        — 저장함
  filter: "전체",      // 카테고리 필터  — 저장 안 함
  editingId: null     // 편집 중 항목 id — 저장 안 함
}
```

`filter`와 `editingId`는 **데이터가 아니라 일시적 UI 상태**다. 특히 "편집 중" 상태가 저장되면 다음 실행 시 비정상 상태로 복원될 수 있다.

### 5.3 저장 형식

- **저장소**: `localStorage`
- **키**: `todo-app:v1`
- **값**: `todos` 배열의 `JSON.stringify` 결과

> 키에 `:v1` 접두사를 두는 이유: 저장 형식이 바뀔 때 `v2`로 넘기며 마이그레이션을 연습할 수 있고, 같은 출처(origin)의 다른 실습 파일과 키가 충돌하지 않는다.

### 5.4 저장하지 않는 것

**진행률은 저장하지 않는다.** `todos`로부터 매번 계산한다. 파생값을 저장하면 원본과 어긋날 수 있으며, "파생 상태는 저장하지 않는다"는 원칙 자체가 학습 대상이다.

### 6.2 편집 중 포커스 처리

전체 재렌더 방식(7.1 참조)에서는 재렌더 시 편집 중인 `<input>`이 DOM에서 교체되어 포커스와 커서 위치가 사라진다.

**해결**: `editingId`를 상태에 보관하고, 렌더 직후 해당 항목의 입력 필드에 포커스를 복원한다.

> 별도 DOM 조작으로 재렌더를 우회할 수도 있으나, 의도적으로 상태로 해결한다. "UI의 모든 것은 상태로 표현된다"는 것이 이 앱의 핵심 학습 목표이기 때문이다.

## 7. 아키텍처

### 7.1 렌더링 방식 — 단일 상태 + 전체 재렌더

```
state 변경 → localStorage 저장 → 구독자 알림 → render() → DOM 전체 갱신
```

**채택 근거**: 항목이 10~20개 규모라 전체 재렌더 비용이 사실상 0이다. 프레임워크가 가상 DOM으로 해결하는 문제가 이 규모에서는 발생하지 않는다. 동시에 "상태가 진실, DOM은 그 결과물"이라는 멘탈 모델은 이후 React·Vue로 넘어갈 때 그대로 이어진다.

**검토 후 기각한 대안**

| 대안 | 기각 사유 |
|---|---|
| 명령형 DOM 직접 조작 | 진실의 원천이 상태 배열과 DOM 두 곳에 생긴다. 카테고리 필터와 진행률이 얹히면 동기화 버그가 발생한다 |
| 웹 컴포넌트 (Custom Elements) | 이 규모에 과설계. Shadow DOM·라이프사이클 등 todo 앱과 무관한 개념이 학습 초점을 흐린다 |

### 7.2 파일 구조

```
Study02_ToDoList/
├── index.html
├── style.css
├── test.html              # 순수 함수 자동 테스트
├── js/
│   ├── storage.js         # localStorage 입출력
│   ├── store.js           # 상태와 변경 함수
│   ├── render.js          # 상태 → DOM
│   └── main.js            # 이벤트 연결 및 조립
├── docs/
└── README.md
```

### 7.3 의존 관계

```
main.js  ──사용──▶  store.js  ──사용──▶  storage.js  ──▶ localStorage
   │                   │
   └──사용──▶  render.js  ◀──상태를 인자로 받음──┘
```

의존은 한 방향으로만 흐르며 순환이 없다. `render.js`는 아무것도 import하지 않는 순수 함수의 모음이므로, 가짜 상태를 주입해 독립적으로 테스트할 수 있다.

### 7.4 모듈 계약

#### `storage.js` — localStorage를 아는 유일한 파일

```js
load()        // → Todo[]   (데이터가 없거나 파싱 실패 시 [])
save(todos)   // → void
```

저장소 접근을 한 곳에 격리한다. 추후 IndexedDB나 서버 API로 교체하더라도 이 파일만 수정하면 된다.

#### `store.js` — 상태의 소유자

```js
getState()                  // → { todos, filter, editingId }
addTodo(text, category)
updateTodo(id, text)
toggleTodo(id)
removeTodo(id)
clearCompleted()
setFilter(category)
setEditing(id | null)
subscribe(listener)         // 상태 변경 시 호출될 콜백 등록
```

**모든 변경 함수는 동일한 3단계를 거친다**: 상태 갱신 → `storage.save()` → 구독자 알림.

이 규칙이 한 곳에 고정되어 있으므로 "저장을 깜빡함" 또는 "화면 갱신을 깜빡함" 류의 버그가 구조적으로 발생하지 않는다.

`subscribe`는 리스너 배열 하나로 구현되는 10줄 내외의 코드다. 없이도 동작하지만(핸들러마다 직접 `render()` 호출), 호출을 누락하는 순간 화면과 데이터가 어긋난다. 이 작은 장치의 가치를 체감하는 것이 학습 목표의 일부다.

#### `render.js` — 상태를 화면으로

```js
renderList(todos, filter, editingId)
renderProgress(todos)
```

#### `main.js` — 조립과 이벤트 연결

### 7.5 이벤트 위임

목록 컨테이너에 리스너를 **하나만** 등록한다. 각 버튼은 `data-action`으로 식별한다.

```html
<li data-id="1735800000000">
  <input type="checkbox" data-action="toggle">
  <button data-action="edit">✎</button>
  <button data-action="remove">🗑</button>
</li>
```

```js
list.addEventListener("click", (e) => {
  const action = e.target.dataset.action;
  if (!action) return;
  const id = e.target.closest("li").dataset.id;
  // action에 따라 store의 해당 함수 호출
});
```

**근거**: 재렌더로 `<li>`가 통째로 교체되어도 리스너를 다시 등록할 필요가 없다. 항목마다 리스너를 거는 방식이었다면 재렌더마다 리스너 중복 등록 또는 누수가 발생한다. 전체 재렌더 방식(7.1)과 이벤트 위임은 서로를 필요로 하는 관계다.

## 8. 비기능 요구사항

### 8.1 기술 제약

- **프레임워크·라이브러리 사용 금지.** 순수 자바스크립트만 사용한다.
- **빌드 도구·npm 의존성 0개.**
- ES 모듈(`import` / `export`)로 파일을 분리한다.
- **실행 방식**: 로컬 정적 서버 (VS Code Live Server, `npx serve` 등)
  - `file://` 직접 열기는 지원 대상이 아니다. ES 모듈이 CORS 정책으로 차단되며, 모든 로컬 파일이 동일한 `localStorage` 공간을 공유해 다른 실습 파일과 충돌할 수 있다.
- **대상 브라우저**: 최신 Chrome / Edge / Firefox

### 8.2 오류 처리

| 상황 | 처리 |
|---|---|
| `localStorage`에 깨진 JSON | `try/catch`로 포착 후 빈 배열로 시작. 콘솔에 경고 출력 |
| `localStorage` 접근 불가 (사생활 보호 모드 등) | 앱은 정상 동작하되 "저장되지 않습니다" 안내 표시. 흰 화면으로 중단되지 않을 것 |
| 저장 용량 초과 | `try/catch`로 포착하고 사용자에게 안내 |
| 빈 입력 / 공백만 입력 | `trim()` 후 거부 + 시각적 피드백 |
| 200자 초과 입력 | 입력 단계에서 제한 |
| 존재하지 않는 id로 조작 | 조용히 무시 (`return`) |

### 8.3 보안

**할 일 텍스트는 반드시 `textContent`로 삽입한다. `innerHTML`을 사용하지 않는다.**

`innerHTML`을 사용하면 `<img src=x onerror=alert(1)>` 같은 입력이 실제로 실행된다. 혼자 사용하는 앱이라 실질적 공격자는 없으나, **"사용자 입력을 `innerHTML`에 넣지 않는다"는 습관을 들이는 것**이 이 프로젝트에서 얻을 가장 실무적인 가치다. 따라서 선택이 아닌 **요구사항**으로 명시한다.

### 8.4 성능

10~20개, 최대 수백 개 항목에서 체감 지연이 없을 것. 전체 재렌더 방식으로 충분하다.

### 8.5 접근성

- 모든 입력 요소에 `<label>` 또는 `aria-label`을 연결한다.
- 마우스 없이 **키보드만으로** 추가·완료·수정·삭제가 가능할 것.
- 진행률 막대에 `role="progressbar"`와 관련 ARIA 속성을 부여한다.

## 9. 검증 계획

테스트 프레임워크는 사용하지 않는다(의존성 0 제약). 두 층으로 검증한다.

### 9.1 자동 테스트 — `test.html`

외부 의존이 없는 순수 계산 로직을 `console.assert`로 검증한다.

### 9.2 수동 검증 체크리스트

DOM과 `localStorage`가 얽힌 동작은 직접 확인한다.

- [ ] 할 일 추가 → **새로고침** → 항목이 그대로 남아 있다
- [ ] 완료 체크 → **새로고침** → 체크 상태가 유지된다
- [ ] 할 일 수정 → **새로고침** → 수정된 텍스트가 유지된다
- [ ] 편집 중 **Esc** → 원래 텍스트로 복원된다
- [ ] 편집 중 다른 곳 클릭 → 변경 내용이 저장된다
- [ ] 필터가 `공부`인 상태에서 항목 삭제 → 진행률이 **전체 기준**으로 올바르게 갱신된다
- [ ] 필터를 전환해도 진행률 수치가 변하지 않는다
- [ ] 할 일 0개 → "첫 할 일을 추가해 보세요" 안내가 뜬다
- [ ] 필터 결과만 0개 → 해당 카테고리를 언급하는 다른 안내가 뜬다
- [ ] 완료 항목 0개 → "완료 항목 비우기" 버튼이 비활성화된다
- [ ] 완료 항목 비우기 → 미완료 항목은 남고 완료 항목만 사라진다
- [ ] 빈 입력으로 추가 시도 → 등록되지 않고 시각적 피드백이 나타난다
- [ ] `<script>alert(1)</script>`를 할 일로 추가 → **문자열 그대로 표시**되고 실행되지 않는다
- [ ] 키보드만으로 추가 → 완료 → 수정 → 삭제가 모두 가능하다
- [ ] 전체 흐름 수행 중 콘솔 에러가 0건이다

## 10. 주요 결정 기록

| # | 결정 | 근거 |
|---|---|---|
| D-1 | 단일 상태 + 전체 재렌더 | 10~20개 규모에서 비용이 사실상 0이며, 이후 프레임워크로 이어지는 멘탈 모델을 학습할 수 있다 |

| D-7 | 이벤트 위임 사용 | 전체 재렌더 시 리스너 중복 등록·누수를 방지한다 |
| D-8 | `file://` 미지원, 로컬 서버 전제 | ES 모듈 사용과 `localStorage` 격리를 위해 필요하다 |
| D-9 | `innerHTML` 금지를 요구사항으로 명시 | 실무 반사신경을 들이는 것이 이 프로젝트의 핵심 가치 중 하나다 |
| D-10 | 실행취소 미구현 | 되돌리기 스택은 별도 학습 주제다 |
